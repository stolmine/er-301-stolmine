# v0.7.0-stolmine.9.2.1 implementation plan

Patch release after v9.2.0 (sequencer + multi-output framework). Seven
quality-of-life items, all already in `TODO.md` with file:line
evidence. This doc is the execution playbook: order, commit cadence,
per-item edit lists, risk flags, release flow.

Branch: `develop`, starting at `ec02869` (post-9.2.0).

## 0. Pre-flight: open questions to resolve before coding

Two decisions block code-level work; everything else can proceed in
parallel with them.

1. **Item 3 (gate-len `0` in random pool): uniform vs weighted.**
   **Recommendation: uniform**, seven entries `{0, 0.0625, 0.125,
   0.25, 0.5, 1.0, 2.0}` (so `dist(0, 6)`). Rationale: the existing
   transpose palette (`ActionApply.cpp:121-124`) already weights
   musically by duplicating entries; if weighting is wanted later,
   do it the same way (literal repetition, no distribution math).
   For v9.2.1, keep the change one-line per side and stay symmetric
   with the existing pool style. ~1/7 rest density is musically
   conservative.

2. **Item 7 (TXo passthrough default): on or off.**
   **Recommendation: default on** (bias = 1.0, current behavior).
   Existing presets break silently if off becomes the default --
   anyone with a TXo TR routed through their chain to drive Out1
   loses audio on upgrade with no UI hint. Default on is also the
   obvious mental model for a unit that's been "send + passthrough"
   since it shipped.

Mark both decisions as locked at the top of `TODO.md` when starting
the patch cycle.

## 1. Implementation order

Ordered by: blast radius, hardware-only verification cost, and
whether the change is graph-side (needs careful audio-thread
reasoning) vs UI-side.

| # | Item | Why this slot |
|---|---|---|
| 1 | **Item 6** shift+HOME multi-slot reset | One-line edit, fully testable in emu, no modal interactions. Warm-up. |
| 2 | **Item 3** gate-len `0` in random pool | Lua + C++ in two files, both trivial, new bench test possible. Touches audio thread but only a constant array. Zero risk. |
| 3 | **Item 4** mark vs edit collision + audit | UI-only, narrow, but the audit (other modal-entry sites) requires reading subPressed / subReleased / encoder paths. Do early so any deeper refactor surfaces. |
| 4 | **Item 1** picker `shiftPressed` + exit-tagging refresh | Independent of sequencer. Sub-bug 1 fix is one line, sub-bug 2 is `if/else` branch swap + Timer.after wrap. Together because they share `toggleFavoritesEditMode()`. |
| 5 | **Item 2** BPM latch UP-release + onHide reset | UI-only but interacts with Settings persistence and onHide ordering. Hardware verify required (user reports CANCEL doesn't release on hardware despite the code being correct; investigate that first before adding UP). |
| 6 | **Item 5** ENTER-in-edit admin Setting | Needs Settings init + Interface menu + GridView branch. Touches three files but the change in each is small. Lands late because it's net-new state; the bench needs to be robust against it (the existing pcall guard pattern is the reason this is safe). |
| 7 | **Item 7** TXo passthrough toggle | Most invasive: requires a new ViewControl pattern (Multiply + Fader on ParameterAdapter), modifies the graph topology of two units, has on/off behavior that needs hardware-with-TXo verification. Last so it doesn't gate the easy items. |

Items 1-6 land first; item 7 can ship as a follow-up patch if
hardware-with-TXo verification slips.

### 3.7 Item 7: TXo passthrough toggle

**Widget research conclusion**: no existing "binary toggle on
top-level view" ViewControl. Available options:
- `Gate` (`xroot/Unit/ViewControl/Gate.lua`): needs Comparator +
  Branch, is a cv-driven gate visualization. Overkill.
- `Fader` over a `Multiply`'s gain parameter: works, visually says
  "0..1 passthrough", uses two encoder columns of space.
- `OptionControl` (menu-side only): wrong layer; user asked
  top-level.

**Recommended path**: graph + Fader on a `ParameterAdapter`
driving a `Multiply` on the output:

- C++ untouched. All Lua.
- `onLoadGraph`: insert `app.Multiply()` named `passthrough`
  between `txoTR:Out` and `self:Out1`. Add `ParameterAdapter`
  named `passthroughGain` with `Out` tied to one side of the
  multiply. Initial bias = 1.0 (= passthrough on).
- `onLoadViews`: add a `GainBias` ViewControl named `passthrough`,
  `biasMap = Encoder.getMap("unit")` clamped 0..1, `biasPrecision
  = 2`, `initialBias = 1.0`. Sub-bar label "passthrough". Insert at
  the front of `expanded` views list (before `"port"`).
- TR shape: identical Multiply + Fader.
- CV shape: same. CV's gain already exists as a parameter; the
  toggle is a separate level after gain.

Default 1.0 preserves current behavior (decision §0.2).

**Why not a hard binary toggle (Comparator on/off)?** Continuous
gain has the same UX with no widget innovation needed, plus it
gives crossfade for free. Pure on/off is a one-line override away
(`biasMap` discrete-stepped).

**Hardware verification gate**: with TXo connected, toggle to 0.0;
assert In1 -> Out1 silent; assert TR gate detection still fires
(LED on TXo); assert CV stream still drives V/oct downstream.
Cannot validate in emu without a TXo bus simulator.

## 4. Bench / test strategy

- **Existing bench (17/17) covers**: L1 set/get, L2 predicates /
  actions (PRED_PROBABILITY, APPROX, FIRE, CHANGED + ACTION_MUTE),
  multi-slot transport, marker semantics. Does NOT exercise
  ACTION_RAND (skipped because non-deterministic) and does NOT
  exercise the UI layer (GridView modal state, picker, Settings).
- **New bench test for item 3** (gate-len random pool): seeds
  `slot.rng`, runs ACTION_RAND repeatedly on a g1L column, asserts
  a 0.0 appears in the distribution. Brings bench to 18/18.
  Justified because (a) the change is a one-line constant-array
  edit easy to silently revert in a future refactor, (b) test takes
  milliseconds.
- **No new bench coverage for items 1, 2, 4, 5, 6**: all are
  UI-thread modal-state machines the bench cannot reach. Manual emu
  test plan instead (see §5).
- **Cadence**: run bench after every commit. `make` from repo root
  (parallel by default per `Makefile:9`); emu boot prints bench
  results from `xroot/boot/start.lua:50`.

## 6. Release flow

1. Final TODO update: edit `TODO.md` to mark the seven items
   "shipped in 9.2.1" (move them to a CHANGELOG section or strike
   through; preserve the v0.6.16 port and crash-report items).
   Commit as **C7** "TODO: mark .9.2.1 items shipped". Optional but
   keeps history honest.
2. Tag: `git tag -a v0.7.0-stolmine.9.2.1 -m "v0.7.0-stolmine.9.2.1"`.
   `FIRMWARE_VERSION` derives from `git describe`
   (`scripts/env.mk:22`), so the tag is the version bump.
3. Build: `ARCH=am335x PROFILE=release make firmware-clean && make
   firmware`. `MAKEFLAGS += -j$(shell nproc)` (`Makefile:9`) gives
   parallel firmware + mods + core + teletype + txo + multiout.
   Output: `release/am335x/er-301-v0.7.0-stolmine.9.2.1.zip`.
4. Smoke test on emu (`make emu`): bench should print 18/18 at boot.
   Hardware sideload zip; smoke test each medium-risk item per §5.
5. Draft release: `gh release create v0.7.0-stolmine.9.2.1 --draft
   --title "v0.7.0-stolmine.9.2.1" --notes-file <release-notes.md>
   release/am335x/er-301-v0.7.0-stolmine.9.2.1.zip`. Release notes:
   seven bullets, one per item, user-visible behavior change (not
   file:line).
6. SD copy command:
   ```
   cp release/am335x/er-301-v0.7.0-stolmine.9.2.1.zip /mnt/ER-301/firmware/ && sync
   ```
7. Promote draft -> published only after hardware smoke confirms
   items 1, 2, 4, 7 behave correctly. Push commits + tag to remote
   at the same time.
