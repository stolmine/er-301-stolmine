# Hold mode scene rework: implementation plan

**Status:** scope locked 2026-05-31 on `feature/hold-mode-scenes`.
**Companion to** `hold-mode-scenes.md` (brainstorm + locked design
decisions). This doc is the working spec for the build.

Hold mode is being **replaced entirely** with a scenes-based
performance surface. The physical hold switch on the front panel
now enters scene Performance view; everything users do today in
hold mode (pinsets etc.) goes away as a concept. Pinsets are not
migrated; users start fresh.

---

## State model

Scene state lives **per chain root** (one independent scene store
per chain). Each chain root currently owns a `PinView`; that gets
replaced by a `SceneView`. The `SceneView` owns:

```
SceneView
+- sceneCount: int (>=0, max 16)
+- scenes[1..sceneCount]: Scene
+- cvInput: source ref (or nil if unset)
+- crossfaderA: int  (index into scenes, or 0 = base)
+- crossfaderB: int  (index into scenes, or 0 = base)
+- morpher: app.ParamSetMorph (native, drives audio-thread apply)
+- baseValues: { [paramHandle] = float } (snapshot for fallback)

Scene
+- name: string (user-renamable, autogenerated default e.g. "S1")
+- deltas: { [unitInstanceKey] = { [controlId] = float } }
```

**Why per-chain:** each chain gets its own crossfader CV
assignment, so a percussion chain can be scene-controlled by one
input while a melodic chain follows a different one. This is more
powerful than a global crossfader, matches the existing per-chain
PinView model, and lets the user combine independent scene
controls across chains for layered performance.

**Why deltas-only:** at 16 scenes max with typically a handful of
delta'd params per scene, full-state snapshots would waste space
and force a slow re-apply when switching crossfader assignments.
Deltas + a base value map keep storage tiny and the apply step
incremental.

## Engine apply mechanism

The existing native primitive `app.ParamSetMorph` (used by
`MasterFader` in PinView) already does the heavy lifting: it
holds a list of `(param, targetValue)` tuples and applies a morph
value [0..1] to all of them on the audio thread, interpolating
each param toward its target. The user encoder drives the morph
value in MasterFader; for scenes we drive it from CV instead.

Two practical extensions needed:

1. **Two-endpoint morph per param.** Existing `ParamSetMorph`
   morphs each param from `param:save()`-snapshot toward `target`.
   For scenes we need lerp between an A endpoint and a B endpoint,
   which may both differ from the save snapshot. Two options:

   - **(a) Reuse ParamSetMorph as-is**: pre-compute the linear
     blend in Lua on every crossfader change, push as the new
     "target", set morph value = 1. Updates happen at control-rate
     (whenever CV crosses a threshold). Cheap for the expected
     scale but slightly grainy on fast CV.
   - **(b) Add `app.SceneBlend` native primitive**: holds
     `(param, endpointA, endpointB)` tuples + a CV reference;
     reads CV each audio frame, applies `param = lerp(A, B, t)`
     directly. Smoother on fast CV; more C++ work.

   **Recommendation: start with (a)** to validate the UX, move to
   (b) only if grain becomes audible. (a) is also more testable
   since blending happens in Lua.

2. **Per-param endpoint fallback to base.** When a scene is
   assigned to slot A but not B, the B endpoint for any param
   delta'd by A should be the base value (the value the user set
   before entering scene-edit). The scene store maintains
   `baseValues` as the snapshot taken on entering scene-edit;
   endpoint resolution at apply time is:

   ```
   endpointA = sceneA.deltas[unit][control]  or baseValues[param]
   endpointB = sceneB.deltas[unit][control]  or baseValues[param]
   ```

   Only params that appear in EITHER scene's delta set need
   morpher entries; everything else just reads its base value.

## Param classification

Reuse the existing PinView control-type distinction directly. In
PinView, a control becomes either a `Fader` (continuous knob) or
a `Gate` (toggle / momentary) when pinned, via the control's
`getPinControl()` returning a sub-classified wrapper. For scenes:

- **Delta-able** = anything that would return a `Fader`-class
  `pinControl`. Continuous knobs, faders, V/oct, gain,
  sub-display-only continuous params in habitat all qualify.
- **Delta-able with snap** = anything that returns a `Gate`-class
  `pinControl` AND is `toggle` (not `momentary`). Toggles can
  morph by threshold (snap at t=0.5).
- **Not delta-able** = momentary gates, step lists (habitat L1
  grid), file paths, structural selectors.

Implementation: extend each control type's `getPinControl()` (or
add a sibling `getSceneControl()`) to return a sub-classified
wrapper that the SceneView understands. Most existing logic
carries over.

## View hierarchy

Two top-level views inside scene mode, accessed via the hold
switch + navigation gestures:

### Performance view (default on hold-mode entry)

- **M1 ply:** CV input picker. Reuses the same widget the chain
  mixer + unit inputs use (Source.ExternalChooser based). Picker
  surfaces IN1-4, A1-4, G1-4, OUTx, seqN.*, global chains.
- **M2..M6 plies:** scene slots (5 visible per page). Each slot
  shows:
  - Scene name (default "S1", "S2", ..., user-renamable)
  - A / B chip if slot is assigned to a crossfader endpoint
  - Delta count (e.g. "12d") to telegraph slot density
- **Encoder:** moves cursor across plies (M1..M6, page-scrolls
  beyond M6).
- **M-tap on empty ply:** creates a new scene slot AT that ply
  + immediately selects it (cursor moves to it).
- **M-tap on existing slot:** selects/hovers the slot. Cursor
  moves there.
- **S1 ply:** crossfader assignment toggle for selected slot
  ("set as A" / "set as B" / "unset"). Tap cycles.
- **S2 ply:** rename selected slot (opens Keyboard).
- **S3 ply:** "edit" -- dives into Authoring view for the
  selected slot.
- **shift+M:** delete selected scene (with confirmation per
  existing chain-clear pattern).

### Authoring view (mirror of user-mode editing for one scene)

- Identical layout to the user-mode chain editing surface for
  the same chain. Same unit row, same control row, same
  navigation gestures (encoder, M1-M6, S1-S3, dive into unit
  details, etc.).
- **Difference:** any param change made here writes to the
  current scene's delta map instead of to the base parameter
  value. The base value is preserved.
- **Visual cue:** controls that have a delta in the current
  scene render with the existing **pin icon** from hold mode
  (the icon that indicates "this control is in a pinset"). Same
  glyph, repurposed; familiar visual vocabulary for users
  migrating from the old hold mode.
- **UP arrow at top of nav stack:** goes UP out of authoring
  back to Performance view (the equivalent of "exit hold mode"
  in the old model, but staying inside scenes).
- **shift+HOME:** straight up to Performance view from anywhere
  in authoring (matches the picker's reset convention).

## Mode transitions

```
                              (panel hold switch ON)
USER MODE  ----------- enter ----------->  PERFORMANCE VIEW
                                              |     ^
                          (S3 on selected      |     | (UP from top, or
                           slot OR M-tap +    \|/    |  shift+HOME from
                           S3)                 |     |  anywhere)
                                            AUTHORING VIEW

                              (panel hold switch OFF)
PERFORMANCE/AUTHORING --- exit ---------->  USER MODE
```

The hold switch is the single in/out gate for scene mode. Inside
scene mode, navigation between Performance and Authoring is via
gesture only (no second physical control).

## Persistence

Scene state persists per-chain alongside existing chain-root
state. New entries in the chain preset / quicksave schema:

```lua
chain.sceneView = {
  sceneCount  = 3,
  scenes      = {
    { name = "verse", deltas = { [unitKey] = { [ctrlId] = 0.42 } } },
    { name = "drop",  deltas = { ... } },
    { name = "bridge", deltas = { ... } },
  },
  cvInput     = "A1",     -- serialized source ref
  crossfaderA = 1,        -- scene index, 0 = base
  crossfaderB = 2,
}
```

Serialization / deserialization mirrors the existing PinSet
serialize / deserialize pattern (lookup by `unitInstanceKey` +
`controlId`, log warnings for missing references).

When loading a chain preset with `chain.pinView` (the legacy
data), surface a one-time admin overlay: "Legacy hold-mode
pinsets found. These cannot be migrated to the new scene system.
Recreate as scenes? [yes / dismiss]". The pinset data is left in
the preset file but ignored.

## Pin icon integration

The existing hold-mode pin icon (rendered via PinView controls
when a param is part of a pinset) becomes the **delta indicator**
in authoring view. Same glyph, same render path, different
trigger: instead of "control belongs to active pinset," it's
"control has a delta in the current scene." Touch points:

- The unit's control row render checks `sceneView:hasDelta(scene,
  control)` and applies the pin glyph overlay when true.
- The control's value display dims to GRAY7 when at base value,
  brightens to WHITE when delta'd (similar to the picker's
  recency-intensity pattern).
- "Unpin"-style gesture removes the delta from the scene,
  reverting that control to base.

## File layout

```
xroot/SceneView/
+- init.lua             -- SceneView class (per chain root)
+- Scene.lua            -- Scene class (deltas + metadata)
+- Performance.lua      -- Performance view + slot rendering
+- Authoring.lua        -- Authoring view (mirror of user mode)
+- SlotControl.lua      -- Per-scene-slot widget (replaces
                           PinSet UI in M2-M6 plies)
+- InputPicker.lua      -- CV input picker on M1 (wraps
                           Source.ExternalChooser)
+- Apply.lua            -- ParamSetMorph driver + endpoint resolution
```

`xroot/Chain/Root.lua` swaps `PinView` for `SceneView`. Existing
`addPinSet`, `getPinSetByName`, etc. methods become no-ops with
deprecation warnings, kept so legacy presets don't crash.

The legacy `xroot/PinView/` tree stays in the codebase for
reference but is no longer wired into chain roots. Can be deleted
once the new view is proven stable for a release cycle.

## Implementation order

Five phases, each independently testable.

### Phase 1: state model + persistence (1-2 days)

- [ ] `SceneView` class with empty Performance view stub
- [ ] `Scene` class with delta map
- [ ] Hook into `Chain/Root.lua` behind a `usesScenes` flag
  (default false initially so dev work doesn't break existing
  workflows)
- [ ] Serialize / deserialize round-trip via existing quicksave
  hooks
- [ ] Legacy-pinset detection + dismiss overlay

### Phase 2: Performance view UI (2-3 days)

- [ ] `Performance` view rendering with M1-M6 plies
- [ ] `SlotControl` widget (name + A/B chip + delta count)
- [ ] `InputPicker` on M1 (reuses Source.ExternalChooser)
- [ ] Encoder navigation + M-tap selection + slot creation
- [ ] S1 (assign A/B), S2 (rename), S3 (enter authoring)
- [ ] Shift+M delete with confirmation

### Phase 3: Authoring view (3-4 days)

- [ ] `Authoring` view that wraps the chain's existing user-mode
  edit surface
- [ ] Param-write redirect: any control change writes to scene
  delta instead of base
- [ ] Pin-icon overlay on delta'd controls (reuse existing
  pin icon rendering)
- [ ] UP at nav root + shift+HOME to return to Performance
- [ ] Unpin gesture (delete delta from current scene)

### Phase 4: Engine apply + crossfader (2-3 days)

- [ ] `Apply.lua` driver using `app.ParamSetMorph`
- [ ] Endpoint resolution (A target + B target with base fallback)
- [ ] CV input sampled at control rate (Lua-side), morph value
  updated on threshold crossings
- [ ] Crossfader assignment changes trigger morpher rebuild
- [ ] Bench: live CV blends between two scenes; A-only and B-only
  fall back to base correctly

### Phase 5: Polish + cleanup (1-2 days)

- [ ] Performance-view CV-focus visualization per slot (show
  which slot the CV is currently weighting)
- [ ] Delete legacy `xroot/PinView/` tree (or keep with note)
- [ ] Admin setting: confirmation on delete scene (per
  user-preferences pattern)
- [ ] Release notes / CHANGELOG entry for replacing hold mode
- [ ] Bench: full performance flow (create scenes, assign,
  perform, save, reload)

Total estimate: ~9-14 days of focused work, plus an unknowable
amount of "hands-on the thing" iteration as the external collaborator warned.

## Open questions (defer to implementation)

1. **CV input scaling.** CV jacks output 0..10V (= 0..1 normalized
   in the audio buffer). Map directly to crossfader [0..1]? Or
   center on 0 (bipolar input) for "default = mid"? Probably
   unipolar by default with an admin "bipolar input" toggle.
2. **Threshold for control-rate morph updates.** How much CV
   change before we recompute the morpher? Too tight: thrashy
   Lua work. Too loose: visible stepping. Start with 0.01 (1% of
   range), tune by ear.
3. **Cross-chain crossfader sync.** If two chains both pick A1 as
   their crossfader input, do they sync automatically? Probably
   yes (they're reading the same signal); no special wiring
   needed. Mentioned here so we don't accidentally introduce a
   per-chain offset.
4. **Authoring view: what does the standard "save" gesture do?**
   Save the scene to disk? Snapshot current values into the
   scene's deltas? In user mode, save persists the whole chain;
   in authoring scene save should be... probably the same? The
   scene IS part of the chain persistence. Verify during impl.
5. **Encoder behavior in authoring view when on a delta'd
   control.** Encoder edits the delta (writes to scene). What
   about HOME / shift+HOME on the control itself -- HOME could
   mean "remove delta" (revert to base). Decide during impl.
6. **Delete-last-scene behavior.** If user deletes the last scene
   from a chain, can the chain still be saved cleanly? Probably
   yes (sceneCount = 0 is a valid state, scene mode is just
   empty). Verify.

---

## Out of scope for v1

- **Multi-scene blend** (3+ scenes weighted simultaneously). A/B
  is enough per brainstorm decision #1.
- **MIDI crossfader control.** Same gate as the sequencer
  ext-clock plan: revisit when MIDI lands on rpidev.
- **Scene morph automation** (recording crossfader moves into
  the patch as a CV-emitting unit). Separate feature.
- **Per-scene macro controls.** Each scene having its own
  macro/aux value separate from the chain's macros. Would
  require a deeper macro-system rework.
